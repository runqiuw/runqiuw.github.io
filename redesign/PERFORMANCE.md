# 3D 房间性能优化计划

2026-10-28 起草。目标：降低房间的加载时间、交互卡顿、显存和每帧开销，**现有模型细节和小字清晰度不能退步**。画质优先于下面的性能和显存数字。设计决定以 `PLAN.md` 的 Performance budget 为准，本文只记录测量结果和改动顺序；每阶段完成后把结论并入 `PLAN.md`，并从本文删除已完成的项。

## 1. 现状测量

### 测量方法

- 构建后的站点（`npm run build` + :4321 preview），headless Chrome，硬件 GPU（Apple M5，ANGLE Metal），1440×900，1× 像素密度；另测 2× 像素密度和 4× CPU 降速。
- 按固定顺序走 22 步：加载 → 页面各区块 → 全屏房间 → 白天拖动 → 软木板 → 切夜间 → 夜间拖动 → 投篮 → 桌面特写 → 退出。
- 每帧统计 draw call（主画面 / 离屏）、着色器程序链接次数、纹理上传次数；Chrome trace 记录主线程、GPU 进程和 worker 占用；每步结束时用 `footprint` 采样渲染进程、GPU 进程，用 CDP 读 JS 堆。
- 显存无法直接读取，按 WebGL 实际分配的纹理、缓冲、渲染缓冲累加估算；主画布多重采样帧缓冲按公式估算。
- 未测：手机真机、其他 GPU、GPU 实际执行时间、真实网络下载时间。M5 是高端设备，下面的“流畅”不代表弱设备。

### 加载时间线（1×）

| 阶段 | 时间 | 负载 |
| --- | --- | --- |
| HTML 与首屏 | 0–81 ms | 页面立即可读 |
| 空闲回调后下载 `room.js` | 104–131 ms | 23 KB gzip（主 chunk 约 199.6 KB gzip） |
| 建 WebGL、环境图、下载 GLB | 131–172 ms | 64 个 GLB 共 6.6 MB（本机服务器）；显存立刻升到约 262 MB |
| 预热：组装、分批编译与上传 | 0.17–6.0 s | 73 个着色器程序、144 次上传；主线程 16%，最长任务 38 ms；房间这 5.8 s 不显示 |
| 淡入保活 | 6.0–7.8 s | 之后进入按需渲染 |

首次访问（驱动没有着色器缓存）时，同一阶段出现 527 ms 长任务和 400 ms 帧间隔；第二次访问最长任务降到 96 ms。

| 步骤 | 主线程 / GPU 进程 | 每帧 draw | 编译 / 上传 | 备注 |
| --- | --- | --- | --- | --- |
| 页面静止 | 14% / 10% | 372，约 20 fps | – | 论文视频每帧都整场景重画 |
| 滚到 Projects | 17% / 14% | 434（223） | 1 / 13 | 相机飞到新机位踢动植物，约 6 s 内每帧刷新日光阴影 |
| 滚到 Games | 19% / 15% | 438（242） | 9 / 155 | 距离地图加载：多一个 WebGL 上下文和 worker，渲染进程 +115 MB |
| 滚到 Playground | 20% | 431（242） | 0 / 842 | 地图截图贴到软木板 |
| 展开全屏 | 19% / 13% | 601（227） | – | 画布和镜面目标变大，显存 +27 MB |

| 切到夜间 | 峰值 59% / 70% | 923（550） | 8 / 53 | 房间画布 0 次编译，8 次应来自重建地图的 WebGL 上下文（旧工具不分上下文）；百叶窗滚动每帧刷新阴影。首次访问 309 + 132 ms 长任务 |

| 投篮特写 / 出手 | 13–22% | 183–245 | 2 + 4 / – | 首次出手编译引导、粒子、描边程序 |

M5 上各步骤稳态都在 16.7 ms 内；卡顿来自上面的一次性尖峰。

离屏部分按渲染目标分类（2026-10-28 用 `bin/profile-room.mjs` 复测后更正，先前把 242 误认为镜面）：
- **阴影**：白天只有日光投影，每次刷新约 242 draw；夜间 5 盏灯约 563 draw。
- **镜面**：每遍约 374–379 draw，只在镜子可见时绘制。
- 页面各区块上，每次相机飞到新机位都会踢动植物弹簧，之后约 6 s 内每帧刷新阴影。植物和挂毯的摆动只写在主材质的顶点着色器里，阴影深度用默认深度材质、不含摆动，所以这些刷新得到的阴影贴图完全相同。

### 内存与显存

| 项目 | 数值 |
| --- | --- |
| JS 堆 | 8–46 MB，GC 后回落，未见泄漏 |
| 渲染进程 | 270 MB → 地图加载后约 480 MB → 约 380 MB |
| GPU 进程 | 735–875 MB（含 Chrome 自身合成开销） |
| 房间显存（估算） | 1×：354 MB；2× Retina：约 530 MB。新工具按逻辑分配并把画布 4× MSAA 计入，1× 峰值估算 373 MB；方法不同，两者不直接比较 |

1× 显存构成：GLB 1024² 贴图 ×16（`nightstand_essentials` 6 张、`backpack` 7 张等）85 MB；主画布帧缓冲 46 MB；2048² 贴图集 ×2（零食、RTX 3070）43 MB；镜面 MSAA 缓冲 35 MB；日光阴影 32 MB；聚光阴影 ×4 32 MB；印刷品/封面/小贴图 28 MB；屏幕画布 ×5 23 MB；环境图 12 MB；几何 9 MB；镜面目标 8 MB。2× 时帧缓冲升到 155 MB、镜面缓冲 86 MB、镜面目标 23 MB。

GLB 里的贴图压缩后共 2.7 MB，上传后是未压缩 RGBA + mipmap，约为 50 倍。three 0.186 的 PCF 阴影只采样深度纹理，但每张阴影仍分配一张同尺寸 RGBA8 颜色纹理，约 32 MB 未被使用。

### 问题排序

1. 冷启动着色器编译与上传：首访 527 ms 长任务；房间约 6 s 才出现。
2. 切夜间：地图重建（含其着色器编译）、全部阴影逐帧刷新。房间自身的夜间程序已在预热中准备，三种切换场景复测均为 0 次编译。
3. 阴影刷新：植物/挂毯摆动触发的刷新结果不变却每帧发生；任何物体移动都刷新全部亮着的灯；夜间和桌面特写还叠加镜面一遍。
4. 显存：贴图未压缩（分辨率是否高于所需尚未验证）；阴影颜色附件闲置；镜面目标按整屏分配。
5. 距离地图首次加载和主题切换时重建。
6. 拖动时标签位置逐个读写引起的强制布局。

## 2. 原则

- 改动分两类：
  - **等价改动**：理论上画面不变，在确定性状态下要求逐像素一致。
  - **可能有损改动**（缩小贴图、UASTC 等有损转码）：默认不做，必须逐资源试验、人工确认。少数机位通过不能证明全场景无损。
- 不降低像素密度、不减面、不缩小阴影贴图、不减少投影灯、不关镜面、不在运动时降分辨率。
- **受保护内容**：不纳入通用缩尺寸、有损转码或材质合并。
  - 显示器、电视、地图、软木板和其他文字画布：各自保持当前分辨率、过滤方式、色彩空间和材质的光照行为。软木板卡片和封面是受光照的标准材质，不改成无光照；显示器和电视保留现有 2 倍画布密度和 `toneMapped: false`。
  - 零食包装、RTX 3070 标签、床头柜护肤品包装、键帽文字、游戏封面、海报、M1917 扫描纹理。
  - 法线和金属度/粗糙度贴图：现有 GLB 中各有 4 个材质使用。
- 保持现有约束：灯与 `castShadow` 数量不随主题变化、按需渲染、主 chunk ≤ 200 KB gzip、无后处理。

## 3. 修改方案与顺序

### 阶段 1：已完成（2026-10-28）

已实现：摆动只触发重绘；标签宽度批量读取；并行提交着色器预热，无输入时放宽批处理预算；按灯追踪新旧投影包围盒（`room-shadows.ts`），关闭的灯保留未刷新标记；修复投篮物体旧阴影；离屏地图主题重建延后；`snack_stash` 在房间就绪后加载（首屏直接打开 Games 或 `#room` 时仍随首屏加载）。设计结论已并入 `PLAN.md`。

白色贴图统一变体试验已放弃：Research 画面有 46 个像素相差 1 个色阶，冷启动编译从 76 增至 82。

验收结果（M5 硬件 GPU，1×）：
- 确定性截图 120/120 张整图和裁图与基线逐像素一致；39 个状态（含夜间投篮、拖动枕头）的缓存阴影与强制刷新均为 0 差异。
- 三种主题切换场景都是 0 次房间编译、无 GL 错误；就绪即切换不再有 > 50 ms 长任务（原 52 ms）。
- `roomready` 约 5.5 s（原 6.2–7.4 s），未达 3 s 目标；首屏 GLB 6,186,504 bytes（零食 756,268 bytes 在就绪后约 2.9 s 才请求）。
- 页面各区块与全屏拖动回弹不再每帧刷新阴影：日间拖动 88,330 → 0、夜间拖动 184,101 → 0 次阴影 draw；投篮物体运动现在正确刷新阴影（此前漏刷）。首次投篮多 4 次阴影深度程序链接。
- `check:performance`（硬件 GPU，含 `ROOM_MIRROR_PIXELS`、`NO_PARALLEL NO_IDLE`）、`check:mirror`、`check:room`（含 `ROOM_LINKS_ONLY`、`VIDEO_FALLBACK`）、`check:shelf`、`check:hoops`、`check:shadows`、`check:room-memory` 通过。主 chunk 198,515 bytes gzip。
- 未测：手机真机（用户决定本阶段不测）。`check:performance` 默认 SwiftShader 下仍可能因固定等待时间超时；拖动、悬停的等待已改为轮询，桌面时钟等后续步骤在 SwiftShader 下未通过，需用硬件 GPU 运行。

### 阶段 2：独立实验（理论上等价，实现风险高）

每项单独开发、单独验收，不合格就放弃，不与其他项捆绑。

1. **去掉阴影颜色附件。**
   - 自建 `shadow.map`，只保留深度纹理（WebGL2 允许只有深度附件的帧缓冲）。
   - 必须保留深度比较设置、清屏顺序和零亮度灯的有效比较纹理，并处理 resize 和 `mapSize` 变化后的重建。
   - 仓库此前因阴影贴图出现过材质整批漏绘，冷启动 GL 错误检查必须通过。
   - 预计省约 32 MB（1×）。
2. **静态 / 动态阴影分层。**
   - 静态投影物的深度缓存一次，动态刷新时用 WebGL2 `blitFramebuffer` 恢复，再只画会动的物体。
   - 灯的位置或投影变化、静态投影物状态改变时，缓存失效；门、抽屉、百叶窗算动态物体。
   - 静态深度需要每盏灯额外一张同尺寸缓存，显存增量与第 1 项的节省相当，可能全部抵消。
   - three 内部的清屏顺序无法安全接入时放弃。
3. **镜面目标按投影包围盒分配。**
   - 像素密度不变，只分配镜子在屏幕上的范围，需要改投影和采样坐标。
   - 必须通过 40 组镜面像素对比、偏心机位检查，以及运动中的模糊、抖动和黑边检查。
4. **合并静态网格。**
   - 只合并不可交互、材质相同的网格。
   - 保留材质、法线、AO、顶点色，以及切墙和夜间隐藏装饰的可见性规则。
   - 可交互物体和屏幕材质保持独立。

### 阶段 3：可能有损（暂缓，逐项经用户同意后再做）

1. **UASTC（KTX2）试验。**
   - 保持原分辨率，不和缩图同时做；从原始素材转换，不在已有 WebP 上叠加损失。
   - 按资源逐个调节质量，人工检查小字、细线、透明边缘和材质表现。
   - 可以避免上传完整 RGBA，但加载时仍有 WASM 转码等 CPU 工作，不同设备选用的 GPU 格式也可能不同。
   - 同时比较下载量和转码耗时。
2. **缩小贴图尺寸。**
   - 前提：阶段 1、2 和 UASTC 之后，真机上显存仍是实际问题。
   - 需求不按包围盒或整张贴图的 UV 面积估算，改为逐像素测量：用调试着色器按 UV 导数 × 贴图尺寸记录每张贴图各区域实际需要的纹素密度。
   - 测量覆盖 hover 放大、开门后的包装、镜子中的视图、镜头移动过程、斜视角和横竖屏。
   - 只对明确列出的候选逐张试验，受保护内容不在其中，不批量应用。
